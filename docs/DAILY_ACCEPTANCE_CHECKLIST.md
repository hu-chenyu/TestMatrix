# TestMatrix 每日交付验收清单

> 与 `docs/DAILY_PROMPT_GUIDE.md` 配套使用：GUIDE 管任务指令产出，本文件管交付验收。
> 验收方是最后一道防线：编程工具的交付自述是嫌疑陈述，不是事实。所有结论必须亲跑命令、亲核现场，禁止凭自述放行。

---

## 一、验收铁律

1. **亲跑亲核**：`py -m pytest` 必须亲自执行，git 现场必须亲自核对，禁止将编程工具的自述作为验收依据。
2. **测试只增不减**：既有测试因行为变更只能改断言，禁止删除；新增条数必须等于新基线减旧基线。
3. **时序测试禁固定 sleep**：真线程 / 时序 / 并发测试必须轮询终态或 monkeypatch 加速，禁止 `time.sleep(N)` 赌时序。
4. **零非技术表述**：代码、注释、文档、commit message 全程适用，词表以本地私有约定为准。
5. **双文档同步**：交付后 PROJECT_PLAN.md 与 PROJECT_CONTEXT.md 的基线数字必须同步更新。
6. **禁强推**：严禁 `git push -f` / `--force`；已推送的违规提交不得自行 amend 后强推覆盖。

## 二、验收十步

### 步骤1：对齐预期（读文件，不跑命令）

- Read `PROJECT_PLAN.md`：确认当日行任务内容、行数/测试数预估、当前旧基线、上一次提交次数。
- Read `PROJECT_CONTEXT.md`：确认前一日已完成模块表、对应设计决策小节、相关踩坑记录、当前旧基线。
- Read `docs/DAILY_PROMPT_GUIDE.md`：对齐风格铁律与 Git SOP。

### 步骤2：核 git 现场（远程对齐 + 工作区状态）

```powershell
git remote -v
git fetch origin
git --no-pager status
git --no-pager log --oneline -5
git --no-pager diff --stat origin/main
```

确认项：
- 远程指向正确仓库。
- 本地与 origin/main 关系：ahead 1 为正常（当日提交尚未 push）；若 behind 则必须先 `git pull --rebase origin main`。
- 工作区无未提交的源码/测试改动（PROJECT_PLAN.md / PROJECT_CONTEXT.md 的本地修改除外，这两个不进 git）。

### 步骤3：核 commit message（Conventional Commits + 零非技术表述）

```powershell
git --no-pager log -1 --format="%H%n%s%n%b"
```

确认项：
- 格式为 `type(scope): 摘要`，type 取值 feat / fix / docs / refactor / test / chore。
- 标题与 body 纯技术事实，零非技术表述。
- 若含违规表述：尚未 push 则要求 `git commit --amend` 修正；已 push 则按第三节处理口径执行。

### 步骤4：核改动文件范围（只加源码+测试）

```powershell
git --no-pager show --stat HEAD
```

确认项：
- 仅含当日改动的源码文件与测试文件。
- 绝对不含 `PROJECT_PLAN.md`、`PROJECT_CONTEXT.md`、`output/`。
- 任务指令中声明"零改动"的文件不得出现（如 Day26 的 case_manager.py）。

### 步骤5：核代码变更（diff 逐项审查）

```powershell
git --no-pager diff HEAD~1 -- {源码文件1}
git --no-pager diff HEAD~1 -- {源码文件2}
git --no-pager diff HEAD~1 -- {测试文件}
```

逐项核对任务指令中的设计要点：类名、函数签名（含参数与返回值类型）、常量名、埋点位置、边界处理、过渡方案标注。
确认完整 docstring + 类型注解 + 中文逐行注释，无 `print`。

### 步骤6：亲跑全量 pytest（核心验收）

```powershell
py -m pytest -v
```

确认项：
- 输出恰好 `{新基线} passed`、0 failed、0 warning。
- 若条数不符或有 warning：直接打回，禁止放行。

### 步骤7：核当日测试文件明细 + 防 flaky 复跑

```powershell
py -m pytest {当日测试文件} -v
```

确认项：
- 文件内测试总数 = 既有条数 + 当日新增条数，全部通过。
- 任务指令中要求修改断言的既有测试仍然存在（未被删除），断言已适配新行为。
- 新增测试覆盖任务指令列出的全部场景。

**防 flaky 复跑（强制）**：真线程 / 时序 / 并发类核心用例必须连跑 3 次全过。以 Day26 为例，多订阅者、断线回放、心跳三条为核心用例：

首选手动连跑 3 次（零新依赖，项目仅装 pytest-rerunfailures，未确认 pytest-repeat 前禁止为跑该命令安装新插件）：

```powershell
py -m pytest {当日测试文件} -v
py -m pytest {当日测试文件} -v
py -m pytest {当日测试文件} -v
```

仅当已确认环境装有 pytest-repeat 插件时，才可一条命令替代手动三连跑：`py -m pytest {当日测试文件} -v --count=3`。
- 3 次中任一次失败或 flaky：打回，要求编程工具修复时序竞态（如轮询替代固定 sleep、帧数上限保护、autouse 清洁 fixture）后重新验收。

### 步骤8：核本地文档同步（不进 git 但必须更新）

- Read `PROJECT_PLAN.md`：当日行 `[ ]`→`[✓]`、顶部当前进度（天数/基线/提交次数）、第七节进度统计表同步。
- Read `PROJECT_CONTEXT.md`：第 5 节模块表加当日行、第 6 章新增设计决策小节（编号以现有小节顺延为准）、第 7 章追加新踩坑记录、第 10 节变更日志加当日行、第 4.2 节基线更新。
- 任一缺失：打回要求补全。

### 步骤9：核 push 状态

```powershell
git --no-pager log --oneline -3 origin/main
git rev-list --count HEAD
```

确认项：
- origin/main 最新 commit 即本地 HEAD（已 push 成功）。
- `git rev-list --count HEAD` 等于当日提交序号。
- 若本地 ahead 未 push：执行 `git --no-pager push origin main`，成功口径为 `{旧hash}..{新hash}  main -> main`；PowerShell 红字 `NativeCommandError` 为 stderr 误报不算失败；出现 `! [rejected]` 则回步骤2 pull --rebase 后重推；严禁 `--force`。

### 步骤10：远程网页终验

- 浏览器打开 GitHub 仓库 commits 页，确认最新提交标题与短 hash 匹配本地 HEAD。
- 确认提交文件列表与步骤4一致。

## 三、已推送违规提交的处理口径

| 违规提交状态 | 处理方式 |
|---|---|
| **尚未 push**（本地 ahead） | 允许 `git commit --amend` 修正 commit message 或补充遗漏文件后重新提交，再走正常 push 流程 |
| **已 push 到 origin/main** | 立即停止操作，报告验收结果与违规项，由人决策处理方式（revert / 新增修正提交 / 其他）；**验收方禁止自行 `git push --force` 覆盖远程历史** |
| **已 push 且含非技术表述** | 同上，由人决策；验收方在评级报告中标注"已推送违规，待人工决策"，评级为 FAIL |

口径依据：Git SOP 第 4 步明确严禁强推；公开仓库的远程历史修改可能影响其他协作者与 CI，必须由人决策。

## 四、二元评级报告模板

> 使用说明：实际填写时所有占位符必须替换为真实值（真实短 hash、真实测试数、真实日期），禁止残留 `{REMOTE_HASH}` 等占位符。评级为 FAIL 时必须填写第五节打回原因与第六节放行条件。

```
======================================================================
Day{DAY} 验收评级报告
======================================================================
交付方：{编程工具名称}
验收日期：{YYYY-MM-DD}
提交短 hash：{真实7位短hash}
提交序号：第 {COMMIT_NO} 次

【评级】□ PASS    □ FAIL

----------------------------------------------------------------------
一、自动化验收（亲跑命令，非自述）
----------------------------------------------------------------------
[ ] py -m pytest -v：{真实通过数} passed / 0 failed / 0 warning
[ ] 当日测试文件：{既有数}既有 + {新增数}新增 = {总数}，全部通过
[ ] 需改断言的既有测试存在且已适配（未被删除）
[ ] 时序/并发核心用例连跑3次全过（防flaky）
[ ] 无 time.sleep 固定等待（时序测试均用轮询或monkeypatch）

----------------------------------------------------------------------
二、git 现场（亲核命令，非自述）
----------------------------------------------------------------------
[ ] commit message：Conventional Commits，零非技术表述
[ ] 改动文件：仅源码+测试，无 PROJECT_PLAN/PROJECT_CONTEXT/output
[ ] 任务指令声明"零改动"的文件未出现
[ ] 本地与 origin/main 一致（已 push，无 ahead/behind）
[ ] git rev-list --count HEAD = {真实提交数}

----------------------------------------------------------------------
三、代码审查（diff 逐项核对）
----------------------------------------------------------------------
[ ] 核心模块1：{设计要点核对结果}
[ ] 核心模块2：{设计要点核对结果}
[ ] 测试断言：覆盖任务指令列出的全部场景
[ ] 完整docstring + 类型注解 + 中文逐行注释，无print
[ ] 过渡方案已标注"Day{N}替换"

----------------------------------------------------------------------
四、文档同步（本地文件，不进git但必须更新）
----------------------------------------------------------------------
[ ] PROJECT_PLAN.md：当日行[✓] + 进度统计同步
[ ] PROJECT_CONTEXT.md：6.x设计决策 + 7.x踩坑 + 5节模块表 + 10节变更日志 + 基线

----------------------------------------------------------------------
五、打回原因（FAIL 时必填，PASS 时填"无"）
----------------------------------------------------------------------
1. {违规项}：违反{铁律名称}——{具体问题}——{正确做法}
2. ...

----------------------------------------------------------------------
六、放行条件（FAIL 时列出修复后重新验收的检查点）
----------------------------------------------------------------------
- {修复项}修复后重跑 py -m pytest 确认 {真实目标数} passed 0 warning
- {修复项}修复后 git commit --amend（未push）或报人工决策（已push）
- 全部修复后重新走本报告一~四项验收

======================================================================
验收人：__________  日期：__________
======================================================================
```

### 评级判定规则

- **PASS**：第一~四项全部勾选，第五项填"无"。
- **FAIL**：第一~四项任一未勾选，或第五项非空。
- FAIL 后禁止部分放行：必须全部修复后重跑完整验收流程，不得"先 push 后补"。
- 已推送违规提交：评级直接 FAIL，标注"已推送违规，待人工决策"，验收方不自行处理远程历史。

---

## 五、占位符使用规则

- 本文件模板中的 `{DAY}`、`{COMMIT_NO}`、`{真实7位短hash}` 等为模板占位符。
- **实际验收报告中禁止残留任何占位符**，必须替换为当日真实值。
- 真实短 hash 通过 `git --no-pager log -1 --format=%h` 获取。
- 真实测试数通过 `py -m pytest --co -q | Measure-Object | Select-Object -ExpandProperty Count` 获取（或直接读 pytest 输出末尾汇总行）。
