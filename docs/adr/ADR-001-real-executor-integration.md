## 背景与问题

Day52 验收门禁要求"真跑一条 `assert True` 通过 + 结果入库 + Web 可见"，
并特别强调"37 天来所有失败都是模拟器造的字符串，报告解析器从未处理过真实 traceback"。
设计前逐行读了执行器、用例模型、执行链路、报告解析器四个模块，确认现有骨架
（`PytestRunner.build_command` + `run_one`）离可用还差四件事：

1. **进程模型**：`run_one` 是"一次调用一条用例"，编排层在 for 循环里逐条调用；
2. **执行目标来源**：`build_command` 取 `case["script_path"]`，但 `TestCase` 没有这一列、
   `_to_dict` 也不产出它，**生产链路永远回落到 `case_id`**；
3. **结果来源**：只认退出码（0/1/其他），没有解析真实结果产物的通路；
4. **超时**：`subprocess.run(timeout=30)` 只杀主进程，xdist worker 会残留。

以下五个决策点按影响面排序，每个都列了当时的备选方案。

### 决策摘要

| # | 决策点 | 选定方案 | 否决的主要备选 |
| --- | --- | --- | --- |
| 1 | 进程模型 | **一个批次一个 pytest 子进程**（chip 用例例外） | 每用例一进程（实测 31.4 分钟启动开销） |
| 2 | 结果来源 | **Allure 结果目录**（JUnit XML 兜底） | 行级解析终端输出（文本形状极脆） |
| 3 | `source_ref` 粒度 | **文件路径 + 可选函数名**（一期 1:1） | 行号（漂移频繁）、纯 node id（改名即失效） |
| 4 | 产物隔离 | **批次独立产物目录**，`cwd` 固定项目根 | 共享 allure 目录（并发互相覆盖） |
| 5 | 超时控制 | **三层超时 + 杀进程树** | 只用 `subprocess.run(timeout=)`（残留 xdist worker） |

## 决策

### 决策 1：一个批次一个 pytest 子进程（而非每用例一个进程）

- **选择**：批次级单进程，用多个 `source_ref` 作为目标路径一次性传入。
  仅 `case_type=chip`（串口/telnet 用例需独占硬件）保留单用例进程模式，作为显式例外。

- **备选方案与取舍**：

| 方案 | 实测/预估代价 | 结论 |
| --- | --- | --- |
| 每用例一进程（现状 `run_one`） | 单文件冷启动实测 1595 ms；1180 条仅启动开销 ≈ 31.4 分钟 | 否决，27 倍浪费 |
| 批次级单进程 | 107 条目录实测 7.2 s；全量单进程约 70 s | **采纳** |
| `pytest.main()` 进程内调用 | 无法隔离崩溃；插件/trace 全局状态跨次残留 | 否决 |
| 长期常驻 worker + 协议交互 | 需自研测试调度协议，且 pytest 无此官方接口 | 否决，属过度设计 |

- **理由**：pytest 进程的固定启动开销（解释器 + conftest + 插件加载）约 1.5 s，
  与用例数无关。每用例一进程把这个开销乘以用例数，是纯粹的浪费。
  保留 chip 例外是因为串口/telnet 用例的物理独占性无法用单进程表达。

### 决策 2：结果来源用 Allure 结果目录，JUnit XML 兜底，行级解析只做实时进度

- **选择**：主数据源 `--alluredir` 产物目录（复用既有 `ReportAnalyzer.parse_results_dir`）；
  `allure-pytest` 不可用时降级到 `--junitxml`；终端行级解析**仅**用于 SSE 实时进度，
  **绝不作为结果来源**。

- **备选方案与取舍**：

| 方案 | 优点 | 致命缺点 |
| --- | --- | --- |
| 行级解析终端输出 | 唯一能实时 | 文本形状极脆（`-q` 级别/宽度换行/颜色码/xdist 前缀）；无参数化、无标签；pytest 改版即失配 |
| JUnit XML | pytest 长期稳定输出，零新增依赖 | 无 labels（severity/feature 拿不到）、无 parameters 数组、failure 文本不含附件；**项目已有更完整的 Allure 通路，等于重写解析器** |
| Allure 结果目录 | traceback 原样完整、labels/parameters 原生、毫秒时间戳；**`ReportAnalyzer` 已实现且被 1207 条测试覆盖** | 需保证批次目录隔离（已由决策 4 解决） |

- **理由**：本项目**已经有 Allure 全链路**（`allure-pytest` 在 requirements、
  `AllureResult` 数据类、`scan_results_dir`/`parse_results_dir` 均为 Day11 既有实现）。
  真实执行是"换一个数据来源喂给它"，不是新写一套解析器。
  而行级解析的脆弱性本项目**当日刚实测吃过亏**：调试命令时把 `-p` 放在 `--` 之后，
  pytest 直接报 `file or directory not found: -p`——**命令与输出的文本形状极脆**，
  这种东西不能当权威数据源。
  实时进度本身注定不准（准确进度需要自研插件，Day56 才做），因此明确标注为过渡方案。

### 决策 3：`source_ref` 存"文件路径 + 可选函数名"，不存行号、不只存 node id

- **选择**：`test_cases` 新增 `source_ref`（**String(512)**，可空，默认 None），值为
  `tests/x.py` 或 `tests/x.py::TestC::test_y`。一期 1:1，1:N 演进走新增关联表。
  列注释与 `src/db/models.py` 保持一致：
  "用例关联的测试脚本路径（pytest 可执行目标），为空表示该用例不可被 pytest 执行"。

- **字段类型为何定为 String(512) 而非 Text（Day46-fix 定稿）**：

  | 考量 | 结论 |
  | --- | --- |
  | 实际长度 | 仓库相对路径 + `::函数名` 正常不超 200 字符，512 留足余量 |
  | 异常输入拦截 | MySQL 严格模式下 VARCHAR(512) 有长度校验，异常超长值在库层即报错；Text 无长度上限，异常数据静默落库 |
  | 录入侧兜底 | Day47 在录入通道（YAML/Excel/创建接口）加长度校验，超 512 字符在录入时即拒绝，不让异常值走到库层 |
  | 跨库一致性 | VARCHAR(512) 是 SQLite/MySQL 通用类型，与本项目其余列（如 `case_id` String(64)）风格统一 |

  **注意**：SQLite 不实现 VARCHAR 长度约束，`String(512)` 在 SQLite 上只是声明、
  不做拦截（Day46 已用测试钉住这一事实），真正的拦截依赖 MySQL 严格模式与 Day47 的录入侧校验。

- **备选方案与取舍**：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 只存文件路径 | 最稳定，改名函数不受影响 | 无法"只重跑一个用例"，全文件重跑 |
| 文件路径 + 行号 | 定位最细 | **行号漂移比改名更频繁**（改一行代码就变），且 pytest 不接受行号作执行目标 |
| 只存 pytest node id | 与 allure 产物天然对齐 | **函数改名即失效**（存量大则需全量回填）；参数化 id 含运行时值，跨环境不稳定 |
| 文件 + 函数（选定） | `pytest -- file::func` 直接可跑；函数级粒度覆盖高频诉求；改名只需改一段 | 仍需处理改名迁移（比 node id 少一个维度） |

- **理由**：它是"**可执行目标**"的最小稳定粒度。稳定性上，行号最不稳定（编辑一次即失效）；
  对齐度上，纯 node id 最贴合 allure 但把易变参数也绑进来。
  文件 + 函数在两者之间取平衡。
- **同时确立的空值语义**：`source_ref` 为空 = 该用例**不可被 pytest 执行**，
  走模拟降级并**显式计数上报**。绝不能再回落到 `case_id`——
  那正是当前 `build_command` 的行为，会让每条用例落 exit code 4（error）。
- **一期 1:1 而非一列多值**：多值串会让查询、判空、去重、校验四处都变复杂，
  属于为不确定需求提前付代价；1:N 演进路径是新增 `test_case_sources` 关联表。

### 决策 4：产物目录按批次隔离，`cwd` 保持项目根

- **选择**：`--alluredir` / `--junitxml` / `stdout.log` / `TMPDIR` 全部落
  `output/executions/<execution_id>/`，运行前清空；**`cwd` 仍是项目根**。
  环境变量按白名单构造（清 `PYTEST_ADDOPTS`、隔离 `TM_DB_*`、设 `PYTHONIOENCODING`）。

- **备选方案与取舍**：

| 方案 | 问题 |
| --- | --- |
| 共享 `output/allure_results`（现状 `pytest.ini` 的 `addopts`） | 并发批次互相覆盖；`ReportAnalyzer.scan_results_dir` 会把多个批次的用例混进一份统计；`--clean-alluredir` 删占用目录触发 WinError 145 |
| 每批次独立 `cwd`（连测试目录一起复制） | `pytest.ini` 的 `testpaths`/`pythonpath=.` 与 `conftest.py` 全部失效，收集不到用例；复制成本高 |
| 批次级产物目录 + `cwd` 固定项目根（选定） | 隔离靠产物路径而非 cwd，`pytest.ini` 语义完整保留 |

- **理由**：隔离的**对象是产物，不是工作目录**。`cwd` 改成批次目录会让
  `pythonpath=.` 失效导致 `import src` 失败——这是"为了隔离把功能弄坏"的典型。
  另外 `PYTEST_ADDOPTS` 必须清空：外部 CI 常注入 `--cov` 等参数，
  残留会污染本次执行的产物目录与判定。

### 决策 5：三层超时 + 杀进程树（不只用 `subprocess.run(timeout=)`）

- **选择**：批次级 L1（默认 3600 s）+ 用例级 L2（事后按 allure `stop-start` 判定，
  默认 300 s）+ 无响应 L3（流式读取空闲默认 900 s）。越界一律**杀整棵进程树**：
  Windows 用 `CREATE_NEW_PROCESS_GROUP` + `taskkill /T /F`，POSIX 用 `os.killpg`。
  看门狗用读取线程内的单调时钟判定，**不用 `time.sleep` 轮询**。

- **备选方案与取舍**：

| 方案 | 问题 |
| --- | --- |
| 只用 `subprocess.run(timeout=)`（现状） | 只终止主进程；`pytest-xdist` worker 作为孙进程继续存活并**继续写产物目录**，直接引发 `WinError 145 / INTERNALERROR`（Day39 起反复出现的老坑） |
| 线程级定时器 + `proc.kill()` | 解决"何时检查"，但 `proc.kill()` 仍只杀主进程，残留问题不解 |
| 信号级杀进程组（POSIX）/ 进程组 + taskkill（Windows）（选定） | 跨平台需两个分支，但这是唯一能真正清干净的做法 |

- **理由**：残留进程不只是资源问题——它会**继续写 allure 产物目录**，
  让下一次运行的 `--clean-alluredir` 失败。本项目已经为这个坑在 `pytest.ini`
  里留了专门注释和"先手动删目录"的处置说明，不应在引入真实执行时再踩一次。

## 后果

### 正面

- 执行耗时的量级从"小时级"降到"分钟级"（决策 1 是最大的一笔收益）。
- 结果解析复用已验证的 `ReportAnalyzer`，不必新写一套容错解析（决策 2）。
- `source_ref` 落地后，`build_command` 恒回落 `case_id` 这个会让真实执行
  **功能性全量 error** 的缺陷被根除（决策 3）。
- 批次产物隔离让并发批次、崩溃重跑、历史追溯都变得可查（决策 4）。
- 超时杀树从机制上消除 WinError 145 的复发路径（决策 5）。

### 负面 / 需要付出的代价

- **执行器需要重写而非扩展**：`PytestRunner` 的 `run_one` 契约（一条用例一个
  `ExecutionResult`）对批次级执行不再适用，需要引入批次级契约
  （`run_batch() -> list[CaseResult]`）。编排层靠 `BaseExecutor` 抽象保持零改动，
  但抽象本身要扩一个方法（6.13 承诺的"编排代码零改动"仍成立，因为
  `_execute_batch_async` 的 for 循环会改为遍历结果列表）。
- **进度不是精确的**：Day50 的实时进度基于行级解析，xdist 下会不准确；
  准确进度要等 Day56 的自研插件。**这是已知的过渡状态，不是最终形态。**
- **平台用例与 pytest 节点的映射需要显式规则**（`source_ref` ↔ allure `fullName`），
  匹配不上的结果必须计入 `unmatched` 并在日志点名，不能静默丢弃（否则通过率虚高）。
- **需要按平台重跑**：一批跑完才知道 `unmatched` 是否为 0，若大量不匹配需要补 `source_ref`。
- **`cwd` 不隔离**是刻意取舍：换来的好处是 `pytest.ini` 语义完整，代价是
  子进程与主进程共享项目目录，必须靠环境变量白名单防止互相污染。
