曲线协议（与实验 A1 同族，便于横向比较）：

1. 命令：`python -m pytest -q --tb=no -n <N>`，N ∈ {1, 2, 4, 8}；每档重复 **3 次取中位**。
2. **不含 `--cov`**：覆盖率插桩会放大锁竞争并显著拖慢耗时（Day60 已验证 `-n 8 --cov` 的稳定性边界），
   耗时口径不混入插桩成本；覆盖率仍由每日验收命令单独把关。
3. 每轮前删除 `output/allure_results`（Windows 上 `--clean-alluredir` 遇残留目录会 `INTERNALERROR`）。
4. 吞吐 = 通过条数 / 中位耗时(s) × 60；加速比 = 1 档中位 / N 档中位；效率 = 加速比 / N。
5. **口径澄清**：`-n 1` 是 **xdist 单 worker 形态**，不是"完全串行直跑"；它与 `-n 4`、`-n 8` 同族可比，
   但与"纯 `pytest`（无 `-n`）"存在一层 worker 进程开销差异，本报告不混用两种口径。

## 二、xdist 并发写锁曲线（1/2/4/8）

全量 1645 条，每档 3 轮：

| 并发数 | 第1轮(s) | 第2轮(s) | 第3轮(s) | 中位(s) | 吞吐(用例/分) | 加速比 | 效率 |
|---|---|---|---|---|---|---|---|
| 1 | 265.51 | 252.62 | 257.31 | **257.31** | 383.6 | 1.00 | 1.00 |
| 2 | 138.17 | 154.18 | 140.84 | **140.84** | 700.8 | 1.83 | 0.91 |
| 4 | 94.74 | 90.74 | 89.88 | **90.74** | 1087.7 | 2.84 | 0.71 |
| 8 | 80.17 | 71.81 | 69.11 | **71.81** | 1374.5 | 3.58 | 0.45 |

三轮全部 `1645 passed / 0 failed`，退出码 0；无 `database is locked`。

### 1. 写锁等待（合成探针，口径透明）

pytest 侧**不存在跨 worker 的写锁竞争**：xdist 给每个 worker 下发独立 basetemp
（`xdist/workermanage.py` 把 `option_dict["basetemp"]` 设为 `<basetemp>/popen-gwN`），
而 `tests/conftest.py` 的会话级隔离把默认库路径钉在 `tmp_path_factory` 下，
因此每个 worker 写的是**自己的会话库文件**。

为回答"如果多线程共写同一个文件库会怎样"，另做**合成写锁探针**：
N 线程对同一个临时 SQLite 文件各写 25 条（`BEGIN IMMEDIATE` + `INSERT` + `COMMIT`，
`busy_timeout=30000` 与 Day60 测试环境取值一致），每档重复 3 轮、取轮间中位：

| 并发线程数 | p50(ms) | p95(ms) | p99(ms) | 最大(ms) | 锁错误 | 相对 1 档 p50 增量(ms) |
|---|---|---|---|---|---|---|
| 1 | 18.465 | 20.547 | 23.542 | 23.542 | 0 | 0.000 |
| 2 | 20.943 | 26.352 | 499.132 | 499.132 | 0 | +2.478 |
| 4 | 20.644 | 29.548 | 959.074 | 1523.770 | 0 | +2.179 |
| 8 | 35.022 | 53.285 | 3626.487 | 5244.371 | 0 | +16.557 |

### 2. 结论

- **中位等待是毫秒级，长尾是秒级**：8 线程共写一个文件时 p50 从 18.5ms 涨到 35.0ms（1.9 倍），
  但 **p99 达到 3.6s、最大 5.2s**——排队一旦形成，个别写入要等整轮事务串行过去。
  全程 **0 次锁失败**，说明 `busy_timeout=30000` 把"抛 `database is locked`"换成了"等"，
  这正是 Day60 修复期望的形态，但**代价是长尾**。
- **pytest 并发曲线不是写锁曲线**：因为各 worker 库相互独立，曲线差异全部来自进程/CPU 侧；
  加速比 1.83 / 2.84 / 3.58 与效率 0.91 / 0.71 / 0.45 表明：
  2 worker 接近线性，4 worker 起被 8 物理核上限与进程启动成本摊薄，8 worker 只剩 45% 效率。
- **对 Day96-100 的直接约束**：若把批次内并发做成"多线程逐条 `run_one` 共写一个 SQLite 文件"，
  会遇到秒级长尾；必须先做 Day65 的 WAL / 写队列，再谈批次并发。

## 七、结论：距护栏还差多少，优化怎么排

护栏两条（Day63 定）：4 worker 吞吐 ≥300 用例/分、平台开销比 ≤1.15。

| 护栏 | 当前 | 差距 |
|---|---|---|
| 4 worker 吞吐 ≥300 用例/分 | 1087.7 用例/分 | **已达标，3.6 倍余量**（套件本身不是瓶颈） |
| 平台开销比 ≤1.15 | 52.5（Day63） | **差 45.7 倍**（不达标项只有一个：平台执行链路） |
| 平台吞吐 ≥300 用例/分 | 24.7（Day63） | 差 12.1 倍 |

**推算（未实测，仅作排期依据）**：

1. 只做批次并发（8 线程逐条 `run_one`）：3973.4s / 8 ≈ **497s ≈ 8.3min**。**开销比的分母必须与分子同口径**：
   分子 497s 是由 Day63 的平台外推（3973.4s）折算而来，分母就应当用同一份 Day63 裸 pytest 中位
   75.73s → 497 / 75.73 ≈ **6.6**；若分母改用今日实测的 `-n 8` 71.81s → 497 / 71.81 ≈ **6.9**。
   两种口径都远高于 1.15，结论不变。**不可把 497s 除以当日 `-n 4` 的 90.74s**——那会得到 5.5，
   属于"Day63 外推分子 / Day64 当日分母"的跨口径混用，既不是哪个基准日的真实开销比，也不可复现。
   该方向仍受第二节的秒级写锁长尾限制。
2. 再做用例合并执行（同一 `source_ref` 一次 pytest 调用、批次内 `-n 8`）：pytest 本体可降到今日实测的
   **71.81s**（已进靶值内）；但若逐条记账仍是 0.36s/条，1645 × 0.36 ≈ **592s** 会把总时长重新拉回 11 分钟量级。
3. 因此**记账成本必须同时降一个量级**（批量写库 + 异步落盘），否则无论并发怎么调都到不了 95s。
   这与 Day63 实验 B 的推论一致："把子进程成本降到 0，平台逐条开销仍是护栏的 5 倍"。

**Day96-100 优化排序（按收益/风险）**：

1. 批次级合并执行（摊薄 1.67s 启动成本，唯一能改变量级的项）；
2. 记账批量化/异步化（把 0.36s/条压到 0.02s 量级）；
3. SQLite WAL + 写队列（**提前到 Day65**，按第二节长尾数据设计，而不是按 P95 设计）；
4. 批次并发度对齐物理核数（8），不用 `-n auto`（核数漂移会让复现性变差）。

## 八、当日测量口径与回归记录

1. **全量回归**：Day64 测量与验收阶段 `-n 8` 共跑 **9 轮**，**全部 1645 passed / 0 failed**；
   其中 4 轮 `0 warning`（含曲线两轮与最终验收轮 65.92s）、4 轮各 1 条、1 轮 2 条，
   warning 来源同一处且每轮落在不同用例：`tests/test_day53_full_integration.py:166` 的
   `UserWarning: 测试库文件仍被占用，未删除`（`WinError 32`，路径为 `popen-gwN` 下的临时库）。
   这 9 轮测量发生在 Day64-fix 之前（当时 `src/` 与 `tests/` 零改动、告警来源文件当日未改），
   热修只放大轮询预算、不触碰该 fixture，故判定为既有的 Windows 文件锁清理噪声，登记为观察项。
   **机制订正（不写"先 reset 再 unlink"这种无效建议）**：该 fixture 的 teardown 已经是
   `DatabaseSession.reset()`（L155）在 `safe_unlink(db_path)`（L166）**之前**，所以再加一次 reset 没有作用；
   真问题是这两步之间还有事件通道/输出通道复位与环境变量还原，后台 daemon 批次线程可能在这段窗口里
   调用 `get_engine()` **重新建出一个指向同一文件的引擎**并持有句柄（此时 `TM_DB_SQLITE_PATH` 尚未被
   monkeypatch 还原），于是 unlink 命中 `WinError 32`。可行的方向是"删前确认执行线程已收尾"
   （join/等终态）或"删失败后短退避重试"，而不是再补一次 reset；`tests/` 禁改日不动，登记待办。
2. **耗时与跑次**：Day64 测量与验收阶段 `-n 8` 的 9 轮 = **曲线测量 3 轮**
   （80.17 / 71.81 / 69.11s，取中位 71.81s）+ **验收与诊断 6 轮**
   （63.08 / 65.46 / 65.92 / 69.43 / 100.24 / 119.18s）。
   最快 63.08s、最慢 119.18s，说明单机单次计时在后台负载下可放大近一倍——这是本报告一律用
   "3 轮取中位"的原因；第六节的靶值判定只采用曲线那 3 轮，不与验收轮混算。
   后续 Day64-fix 复核又跑 3 轮（59.13 / 59.43 / 57.24s，全部 1645 passed / 0 failed），
   计数与耗时另记，不并入本节 9 轮口径。
   **caveat（Day64-fix2 补充）**：这 3 轮全绿只代表"独立环境、顺序执行"的结论，
   不等于并发复核下同样稳定——多份全量同时跑（多 AI 并行复核）时因 CPU 争抢会出现偶发失败，
   单轮失败率约 **25%**，失败点集中在三处已知时序敏感位置：`test_day62_full_chain_integration.py`
   的批次轮询预算（Day64-fix 已放大到 60s）、`tests/api_demo/test_case_manager_cli_demo.py`
   的**共用固定路径库**（xdist 把单文件内的用例也分发到多 worker，多进程同时 `init_db()`
   会在 `create_all` 的"先查后建"上撞车，实测 `-n 8` 稳定出现 5 个
   `table test_cases already exists`；Day64-fix2 已改为每用例 `tmp_path` 独立库 + 删库短退避重试）、
   `tests/test_conftest_hooks.py` 的嵌套 pytest 探针目录命名（挂账 Day65 统一治理）。
   CI 的 `-n 4` 口径是单 job、无并行复核负载，不受该现象影响。
3. **一处口径不一致（登记，未改）**：`tests/conftest.py` 的 `busy_timeout` 注释称
   "`-n N` 并发下多个 worker 进程各持一条连接写同一个文件库"，与实际不符——
   xdist 给每个 worker 下发独立 basetemp，会话库按 worker 分片，跨 worker 不共享文件。
   该注释属 `tests/` 文件，今日禁改；Day65 做 SQLite 加固时顺手订正。
4. **一处文档滞后（已订正）**：`docs/ROADMAP.md` L35 曾把"pytest 钩子与自定义插件、xdist 并发、
   模拟/真实双模式切换"写成"规划中"，而三项均有交付提交（Day55-58）；该文件在 Day64-fix 中
   因 P4-5（测试总数 1586→1645）进入白名单，故同一文件的陈旧能力状态一并订正。
5. **探针口径声明**：第二节的写锁探针是**合成负载**（裸 `sqlite3`，不经 ORM，不含业务逻辑），
   只用于量化"多线程共写一个文件"的锁行为，**不代表平台真实调度开销**；
   其绝对值随机器 I/O 状态漂移（同日 1 档 p50 曾实测 4.1ms 与 18.5ms），故报告只采信同批次内的相对量。
