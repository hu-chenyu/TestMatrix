## 2. 实验方法

### 2.1 覆盖率映射（`CoverageMapper`）

读 `.coverage` 的 SQLite（`file` / `context` / `line_bits` 三表），
解码 `numbits` 位图得行号集，建双向索引：
`test_id → 覆盖文件` 与 `文件 → 覆盖它的 test_id`。
路径两侧统一归一为「相对项目根 + 正斜杠」（`.coverage` 存绝对反斜杠路径，
git diff 给相对正斜杠路径，不归一则永远匹配不上）。

### 2.2 import 拓扑（`ImportGraph`）

用标准库 `ast` 解析 `src/` 全部 `.py`，识别 `import x` / `from x import y` /
`from .x import y`（相对导入按包层级解析为绝对模块名）。
边方向 A→B 表示 A 依赖 B；「修改 B 会影响谁」= 沿**反向**边 BFS 的传递闭包。
循环依赖用 DFS 三色标记检测。`ast.walk` 会走进 `if TYPE_CHECKING` 与
`try/except ImportError` 分支——对影响面分析这是**保守正确**的选择。

### 2.3 用例选择（`RegressionSelector`）

```
选中(F) = 直接覆盖 F 的用例 ∪ 直接覆盖「反向影响面内任一模块」的用例
选中比例 = |选中| / |用例全集|
漏检率   = |直接覆盖 F 却未被选中| / |直接覆盖 F|
```

取**并集**而非交集：真实修改既可能让 F 自身行为变错，也可能让调用方变错，
任一维度漏掉都可能造成回归漏检。

### 2.4 实验样本

按验收口径选 5 个**形态有代表性**的文件（大/小、核心/边缘、直接测试多/少各一）：

| 文件 | 形态定位 |
| --- | --- |
| `src/core/case_manager.py` | 最大文件 + 核心域（2833 行） |
| `src/core/executors.py` | 当日主题模块（执行器，336 行） |
| `src/web/routes/executions.py` | Web 触发入口（865 行） |
| `src/web/config.py` | 边缘配置模块（195 行） |
| `src/common/time_utils.py` | 最小工具文件（89 行，叶子模块） |

## 4. 分析结论

1. **方案可行**：五个文件的选中比例落在 **19.88% ~ 56.92%**（均在 10%-90% 有效区间），
   漏检率全部 0%，说明"覆盖率映射 + import 影响面"的并集选择在本项目上跑得通。
2. **第二维度确有贡献，不是凑数**：import 影响面为每个文件**净增** 163~566 条用例
   （`executors.py` 净增 566 条，是其直接覆盖量的 10 倍）。
   若只按直接覆盖选，`executors.py` 只会选中 55 条（4.66%），而改执行器抽象
   明显会波及编排层与全部 Web 路由——**只靠覆盖率映射会严重漏检**。
3. **import 召回率差异大，可作门禁指标**：`executions.py` 89.61%、
   `time_utils.py` 96.41%（import 维度几乎能覆盖直接覆盖集），
   而 `case_manager.py` 仅 43.79%（大量用例直接调它而不经由它的依赖方）。
   → **"仅靠 import 的召回率"可以直接回答"第二维度值不值得保留"**，
   建议列为 Day94 的工程化指标之一。
4. **叶子的反直觉性**：`time_utils.py` 只有 89 行、是依赖图叶子，
   却被 13 个模块依赖、选中 687 条（56.92%）。**"文件小 = 影响小"是错的**，
   精准回归不能按文件大小挑样本。
5. **全选/全不选确实代表算法有问题**：首版自动挑选规则取"入度最高"得到
   `logger.py`（选中 **100.00%**）、取"最小零入度"得到 `db/__init__.py`
   （6 行空文件，选中 **0.00%**）。两者都落在无效区间，已改为
   **清单优先、规则兜底**的挑选顺序。
6. **覆盖率与精准回归的数据源已打通**：本 POC 证明 `.coverage` 的 per-test
   上下文可用（1207 条映射完整），这是后续 AST 精准回归的数据基础。

## 5. 局限性（**必读，决定这些数字能用到什么程度**）

### 5.1 漏检率恒为 0 是**定义决定的**，不是实验结论

`选中 = 直接覆盖 ∪ 影响面覆盖`，而漏检率的分母就是"直接覆盖"。
**并集的第一项就是分母本身，所以漏检率按定义恒为 0。**
它的真实价值是**回归守卫**（一旦有人把选择公式改成纯 import 召回，立刻变红），
**不是**"算法无漏检"的证据。

真正非恒真的指标是 **仅靠 import 的召回率（43.79% ~ 96.41%）**，
它回答的是"第二维度能召回多少直接覆盖的用例"。引用本报告数字时
必须连同这一点一起说明，否则会把定义产物误读成实验发现。

### 5.2 `.coverage` 默认**没有**每用例上下文（当日踩坑）

pytest-cov 4.1.0 的 `--cov-context` 默认不开启。不加 `--cov-context=test` 时，
`context` 表里**只有一行空串**（收集期覆盖），"用例↔文件"映射根本无从谈起——
本实验首轮就撞上了，`用例数: 1` 看起来像"只有一条用例"。

另：context 名为 `node id|阶段`，形如
`tests/x.py::TestC::test_y[参数]|run`。本 POC 默认只取 `|run`
（setup/teardown 覆盖 conftest 等共享代码，计入会让映射退化成"全量"），
并提供 `--phase` 显式切换口径（对比见 3.5）。

### 5.3 **空上下文不是噪声**，它装着全部导入期覆盖

7 个"零 run 阶段覆盖"文件里，6 个是空 `__init__.py`（0 语句），
**但 `src/db/models.py` 不是**：它有 101 条语句、覆盖率 94%，
却在任何用例名下都不出现。实测它的 `line_bits` **只有 1 行，
且 owner 是空上下文**——ORM 模型的类定义在**导入期**执行，不在任何用例体内。

后果很实在：**改 `models.py`（加列/改字段）时，基于本方案的选择器会认为
"没有用例需要跑"，而实际上几乎所有用例都会受影响。**
这正是 Day45 设计文档中 `source_ref` 必做的原因之一。
→ Day94 必须把"空上下文有行数据但无用例归属"的文件**强制纳入全选**。

### 5.4 没有做变异测试，真值未测

本实验全部是**代理指标**：用"覆盖关系"和"依赖关系"推断"哪些用例该跑"，
**从未验证"改了这个文件之后，到底哪些用例会真的挂"**。
唯一无偏的真值只有一种：改文件 → 跑全量 → 看哪些失败。本 POC 受
"不修改 `src/`"的硬边界约束，未做该实验。

→ **Day94 的验收必须补变异验证**：对 3~5 个文件做真实改动（受控变异），
跑全量取真实失败集合，与选择集对比，**这才是召回率的可信口径**。

### 5.5 循环依赖削弱传递闭包的区分度

检测到 `notification ↔ case_manager` 互依。在环内，修改任一模块都会把另一个
算进影响面，**传递闭包在环上不再有区分度**。当前未阻断（只告警），
但规模变大后环会持续撑大选中面。→ Day94 需定策略：环内模块是否退化为全选。

### 5.6 其他边界

- **1:N 关系未验证**：`source_ref` 尚未落地（Day46 才做），
  "一条用例对应多个测试文件"的场景在本次实验中不存在。
- **xdist 下未验证**：本实验 `--cov-context=test` 关闭了并发；
  Day58 接 xdist 后 context 的产出形态（是否带 worker 前缀）需重新核对。
- **单平台**：全部数据在 Windows 上取得，未在 Linux/macOS 复现
  （路径分隔符归一逻辑已按平台无关编写，但未实测）。
- **覆盖率数据与代码版本绑定**：`.coverage` 反映的是**采样时**的代码；
  代码改动后映射即失效，Day94 必须提供刷新流程（重跑覆盖率是分钟级成本）。

## 6. 对 Day94 工程化的建议

### 6.1 CLI 与输入

- 入口：`py -m scripts.ast_regression_poc --modified-files <files>`，
  直接吃 `git diff --name-only` 的输出，**默认即"改了哪些文件就选哪些用例"**。
- 保留 `--phase` 显式口径（run/all）与 `--output json`（供 CI 消费）。
- `src-dir` / `coverage` 参数保留，工具不绑定本项目路径。

### 6.2 双指标量化（验收口径）

| 指标 | 定位 | 阈值建议 |
| --- | --- | --- |
| 选中比例 | **主指标**（省了多少时间） | 落在 10%~90% 为有效；>90% 说明该改动本就牵一发动全身，应全选 |
| 漏检率 | **回归守卫**（恒 0） | 必须 0；变红即选择公式被改坏 |
| 仅靠 import 的召回率 | **第二维度的价值证明** | <30% 的项目可考虑只保留覆盖率维度 |

### 6.3 必须补的三处工程化处理

1. **导入期文件强制全选**：命中"空上下文有行数据但无用例归属"的文件
   （本项目：`src/db/models.py`），无论选中比例多少一律全选（5.3）。
2. **自动样本过滤**：挑选实验样本时排除选中比例 >90% 与 =0% 的文件（4.5/4.6）。
3. **循环依赖策略**：环内模块的影响面退化为全选，或按环整体处理（5.5）。

### 6.4 数据源演进

- 短期：`--cov-context=test` + `line_bits`（本 POC 方案，可用）。
- 中期：**Day56 的自研 pytest 插件**可同时产出更准的进度与 1:N 归属关系，
  届时用它替代 `--cov-context` 解析，避免"为拿覆盖率数据而跑一次全量"的固定成本。
- 依赖清单导出（Day94 目标之一）：`test_id` + `source_ref` + `impact_reason`
  （直接覆盖 / 影响模块名）三列，直接生成可提交的执行清单。

### 6.5 验收方式

- **必须包含变异验证**（5.4）：受控改文件 → 跑全量 → 真实失败集 vs 选择集。
  没有这一步，"精准回归"只是看起来精准。
- POC 现有 27 条单测可作为工程化实现的回归基线，
  重点复用：`numbits` 编解码往返、相对导入解析、反向影响面 BFS、环检测、
  阶段口径过滤、库外文件跳过、schema 缺失降级。

## 7. 复现方式

```powershell
# 1. 生成带每用例上下文的覆盖率数据（不加 --cov-context=test 无映射可言）
.venv\Scripts\python.exe -m pytest --cov=src --cov-context=test --cov-report= -q

# 2. 跑 POC（默认 5 个代表文件，text 输出）
.venv\Scripts\python.exe scripts/ast_regression_poc.py

# 3. 换口径对比 / JSON 输出 / 指定文件
.venv\Scripts\python.exe scripts/ast_regression_poc.py --phase all
.venv\Scripts\python.exe scripts/ast_regression_poc.py --output json
.venv\Scripts\python.exe scripts/ast_regression_poc.py --modified-files src/core/executors.py

# 4. 单元测试
.venv\Scripts\python.exe -m pytest tests/test_ast_regression_poc.py -q --no-cov
```
